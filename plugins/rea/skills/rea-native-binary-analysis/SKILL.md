# Native Binary Analysis with REA

This skill provides specialized workflows for analyzing compiled native executables, shared libraries, and core crash dumps across Windows (PE/COFF), Linux (ELF), and macOS (Mach-O).

---

## 1. Quick Decision Matrix: Target Routing

| Target Artifact | Primary REA Tool | Engine / Provider | Notes |
| :--- | :--- | :--- | :--- |
| **Go Executable / Library** | `inspect_go_binary` | Built-in (Target-Free) | Extracts compiler version, module paths, embedded build flags. |
| **Rust Binary (`cargo-auditable`)** | `inspect_rust_binary` | Built-in (Target-Free) | Reads `.dep-v0` crate list, rustc commit hash. |
| **Linux ELF (Offline Layout)** | `inspect_binary_layout` | Pwntools / Built-in | Inspects sections, relocations, dynamic symbols, security mitigations. |
| **PE Resources (Windows)** | `inspect_pe_resources` | Built-in (Target-Free) | Traverses resource trees, version manifests, and icons. |
| **Linux Core Dump** | `inspect_recorded_crash` | GDB / pwndbg | Inspects thread states, registers, signals from x86-64 ELF cores. |
| **Compiled Binary (Decompilation)** | `open_binary` -> `analyze_function` | Ghidra / Hopper / IDA / Kuna | Full interactive decompilation, xrefs, and pseudocode. |

## 2. Target-Free Fast Path (No Disassembler Required)

When analyzing modern binaries, compiler metadata and structural layout can often answer questions in milliseconds without starting a disassembler.

### Go Metadata Extraction
```json
{
  "path": "/path/to/binary"
}
```
- Tool: `inspect_go_binary`
- Emits: Go version (e.g. `go1.22.4`), module dependency tree with exact versions, vendor replacements, and architecture settings.
- Preserves raw module bytes and section digests.

### Rust Crate Auditing
```json
{
  "path": "/path/to/binary"
}
```
- Tool: `inspect_rust_binary`
- Emits: Full list of compiled cargo dependencies, crate versions, and rustc build inferences.

### Offline ELF Security Mitigation Check
```json
{
  "path": "/path/to/binary",
  "detail": "summary"
}
```
- Tool: `inspect_binary_layout`
- Reports static mitigations:
  - **NX / DEP**: Non-executable stack.
  - **Canary**: Stack protector cookies present.
  - **PIE**: Position-independent executable.
  - **RELRO**: Partial or Full Read-Only Relocations.

## 3. Stateful Disassembly & Decompilation Workflow

For custom logic, proprietary algorithms, or vulnerability research, initiate an active binary session.

### Step 1: Open Target Binary
```json
{
  "path": "/path/to/target.exe",
  "provider_id": "ghidra"
}
```
- Available `provider_id` choices:
  - `"ghidra"`: Default comprehensive headless decompiler.
  - `"hopper"`: Fast macOS / Linux disassembler.
  - `"ida"`: Connects to local IDA Pro headless or attached MCP backend.
  - `"kuna"`: High-speed export caching provider.

### Step 2: Binary Overview & Procedure Discovery
Query the overall architecture, entry points, and search for target functions:
```json
// Inspect binary headers and sections
binary_overview({})

// Search for procedures by name or regex
search_procedures({
  "query": "Crypto|Auth|Decrypt|Key",
  "limit": 25
})

// Search for referenced strings
search_strings({
  "query": "https://|password|secret|AES",
  "limit": 50
})
```

### Step 3: Decompile and Trace Cross-References
Once a procedure address or name is identified (e.g., `0x1400010a0` or `sub_1400010a0`):
```json
// Decompile function to C pseudocode and assembly
analyze_function({
  "address": "0x1400010a0",
  "include_pseudocode": true,
  "include_assembly": true
})

// Trace callers and callees (cross-references)
xrefs({
  "target_address": "0x1400010a0",
  "direction": "both"
})
```

### Step 4: Value and Call Target Resolution
For indirect calls (vtable dispatch, function pointers, jump tables):
- `resolve_native_call_targets`: Determines possible dynamic dispatch targets.
- `trace_native_values`: Traces register and memory value propagation leading up to critical instructions.

### Step 5: Clean Up Session
Always close the active binary session when complete to release provider locks and free memory:
```json
close_binary({
  "save_snapshot": true
})
```

## 4. Evidence Integrity Checklist
- [ ] Link all function signatures, addresses, and pseudocode snippets to their corresponding `evidence_id`.
- [ ] Explicitly note indirect jumps or unresolvable imports as **Unknowns** rather than guessing target addresses.
- [ ] Differentiate between declared symbol names (from debug info/symbols) and autogenerated names (`sub_XXXXXX`).
